# Model card — OnaRadar adverse-outcome model

> **Trained on SYNTHETIC data only. It must be retrained and re-validated on real DMED data
> before any clinical use.** Exact metrics of the current artifact: `artifacts/metrics.json`.

## Intended use
Decision support for antenatal monitoring: estimates the probability of a composite adverse
outcome so the zone can be **raised** (never lowered) above what the clinical rules give.
The final decision belongs to the doctor. Not a diagnostic device.

## Model
- LightGBM binary classifier, 36 features (`app/risk/features.py`): maternal age, obstetric
  history, chronic flags, booking BMI, distance to perinatal centre, current vitals and labs,
  deltas vs the previous visit, running max BP / min Hb, symptom counts.
- Isotonic calibration on a held-out split; SHAP TreeExplainer for the top-5 factors
  (Uzbek labels in `app/risk/ml.py`).
- Train / calibration / test split **by pregnancy** (no leakage); 5-fold GroupKFold CV on train.

## Label
`adverse_outcome` — composite (severe preeclampsia/eclampsia, postpartum haemorrhage, preterm birth
<34 weeks, stillbirth, neonatal intensive care), generated by a hidden logistic model over risk
factors + deterioration paths + noise (`ml/generate_synthetic.py`). Base rate ≈ 10%.
The hidden latent variables are not features.

## Results on synthetic test set (model 5622c10fe7, 20,000 pregnancies, 174,505 visit rows)
| Metric | Value |
|---|---|
| ROC-AUC (test) | 0.662 |
| PR-AUC (test, base rate 9.7%) | 0.279 |
| Brier | 0.079 |
| CV ROC-AUC (5-fold mean) | 0.648 |
| ROC-AUC by trimester (1 / 2 / 3) | 0.55 / 0.54 / 0.71 |
| ROC-AUC by region (FAR / QQR / TSH) | 0.63 / 0.68 / 0.65 |

Every visit is scored, including early visits before any deterioration has begun, so early-pregnancy
discrimination is low by construction. That is expected: the model is most useful in the 3rd trimester.

## Thresholds
`ML_YELLOW` and `ML_RED` (in `app/risk/thresholds.py`) are chosen on the calibration split:

- **yellow (0.12)** — the highest cut-off (within 0.08–0.20) that keeps the **combined** system
  (rules + trends OR ML) at ≥85% **pregnancy-level** sensitivity: a pregnancy with an adverse outcome
  counts as caught if it is YELLOW/RED at least once from 28 weeks.
- **red (0.35)** — the lowest cut-off where ML-alone precision reaches 60%.

On the test split:

| Combined system (rules + trends OR ML) | Sensitivity | Flagged |
|---|---|---|
| Pregnancy level (flagged at least once from 28 w) | **91.8%** | 73.1% of pregnancies |
| Per visit (every visit, incl. 1st trimester) | 63.7% | 46.8% of visits |
| ML alone ≥ red | 14.7% (precision 61.8%) | 2.3% of visits |

Why pregnancy level: the previous per-visit target (≥90%) needed ML yellow at its 0.08 floor and flagged
~80% of visits, i.e. almost the whole register would be yellow. With an AUC around 0.66, ≥85% *per-visit*
sensitivity is not reachable together with a mostly-green register; per-visit sensitivity is shown above
so this trade-off is visible.

## Demo register (seed) vs. training data
Training data are unfiltered draws from the generator. The demo register (`app/seed.py`) is different:
each mahalla gets 50–60 active pregnancies, every candidate is scored by the real risk engine, and
candidates are kept by zone quota (`ZONE_MIX`: 3–7% red, 20–28% yellow, rest green). This is demo
sampling for a realistic-looking dashboard, not an epidemiological estimate.

## Limits
- Synthetic data reflect our assumptions, not the real population. Real performance is unknown.
- Fairness check by region is shown above; real data must be checked by region, age group and
  rural/urban status.
- Tier A / Tier B split of the yellow rules (see docs/CLINICAL_RULES.md) and the generator's
  prevalence assumptions need clinical review.
